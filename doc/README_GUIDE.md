# README 分层写作规范

本规范用于统一仓库内 README 的职责边界，避免信息重复、层级混乱和过期说明长期残留。

## 目标

- 让读者只看当前目录 README，就能理解本级目录负责什么。
- 让 README 保持短、准、稳定，不承担 TODO、实验报告或历史档案职责。
- 让同一事实只维护一处，其他 README 通过说明来源或链接引用。

## 核心原则

1. 就近说明：每个 README 只解释“当前目录”。
2. 本级边界：README 只说明本级路径下的一层文件和文件夹，不越级展开孙级内部实现。
3. 有序整理：README 要按职责分组说明，而不是把文件名简单罗列一遍。
4. 单一事实来源：同一规则只写一处，其他文档使用链接或一句话引用。
5. 过期即删：失效入口、历史命令、旧目录状态不继续留在 README 中。
6. 短而准：如果一段内容需要频繁更新，通常不应该放在 README。

## README 与其他文档的边界

### README 负责什么

- 当前目录的功能边界。
- 当前目录下一层文件或文件夹的职责。
- 当前目录内长期有效的命名规则、入口约定和维护约定。
- 必要时说明本目录“不负责什么”，避免职责外扩。

### README 不负责什么

- 不记录未完成任务列表。
- 不记录历史变更流水账。
- 不承载实验结论、周报、阶段分析或专利草稿。
- 不复制下级 README 的详细内容。
- 不复制完整 JSON 配置或代码默认参数表。
- 不维护已经失效的命令、路径、入口和兼容说明。

### README 与 TODO 的边界

- 未完成任务进入根 `TODO` 或对应实验目录的 `TODO`。
- README 只记录长期有效的结构、职责、入口和约定。
- 已完成任务不在 README 中长期保留“完成记录”。

## README 默认结构

每个 README 默认优先使用以下结构。若某一节没有实质内容，可以省略，不要为了模板而填空。

### 功能

一句话概括当前 README 所在目录的功能。必要时再补一句“不负责什么”。

### 本级模块职责

只描述当前目录下一层文件或文件夹的职责。

示例：

```md
## 本级模块职责

- `optimizer/`：负责优化主链，包括搜索算法、评估器、梯度估计和优化编排。
- `training/`：负责 surrogate 训练流程，包括 target 构造、训练调用和训练侧对接。
```

不要在上级 README 中展开更深层文件。若需要解释 `optimizer/core/adamw.py`，应进入 `optimizer/core/README.md`。

### 命名规则

说明本目录下文件或目录的命名规律。若无特殊规则，可写：

```md
## 命名规则

- 遵循项目全局 `snake_case` 命名规则。
```

同一类文件应保持命名节奏一致，不使用 `new`、`final`、`tmp`、`test2`、`v2` 这类阶段性词。

## 可选结构

以下小节仅在当前目录确实需要时使用。

### 当前约定

记录长期有效的维护规则、配置规则或行为边界。

### 常用入口

列出当前目录下稳定可用的脚本、配置或主要入口。不写临时命令。

### 输入

适用于脚本、数据、配置、实验产物目录。说明本目录消费哪些上游输入。

### 输出

适用于脚本、数据、配置、实验产物目录。说明本目录产生哪些下游产物。

### 使用建议

给出读者进入本目录后的推荐阅读顺序或操作路径。

### 注意事项

只写长期有效、容易踩坑且不能从代码或配置中直接看出的事项。

## 不同层级的写法

### 根 README

- 回答项目是什么。
- 给出最重要的启动入口和目录地图。
- 不展开所有子系统内部细节。

### 一级目录 README

- 回答该目录在项目架构中的职责。
- 说明下一层模块如何分工。
- 可以给出推荐阅读顺序。

### 二级目录 README

- 回答本目录内文件、子目录、入口脚本或配置模板如何配合。
- 可以写更具体的命名规则和使用约定。

### 更深层 README

- 仅当该目录具有独立工作流、独立命名规则或长期维护边界时才创建。
- 不为单个普通源码文件强行创建 README。

## 何时必须更新 README

出现以下变化时，必须同步检查对应 README：

- 新增、删除、重命名本级文件或目录。
- 修改配置层级、引用方式或字段单一事实来源。
- 修改脚本入口、默认配置路径或输出位置。
- 修改命名规则。
- 删除旧兼容路径或旧入口。
- 改变当前目录职责边界。

## 标准模板

```md
# <目录名> 说明

## 功能

- <一句话说明当前目录负责什么。>
- <必要时说明当前目录不负责什么。>

## 本级模块职责

- `<child_a>/`：<职责说明。>
- `<child_b>/`：<职责说明。>
- `<file_a.py>`：<职责说明。>

## 命名规则

- <说明本目录下文件或目录命名规律。>

## 当前约定

- <只写长期有效的本级约定。>
```

如果某节没有实质内容，应直接省略。

## 专题文档元信息头

本节适用于 `doc/*.md` 这类当前有效专题文档，不强制适用于 README。

所有“当前有效文档”建议在标题下固定写 4 行元信息：

- `状态`
  - 推荐值：`active` / `draft` / `archive`
- `最后验证`
  - 使用绝对日期，例如 `2026-04-03`
- `适用范围`
  - 说明对应模块、流程或版本边界
- `单一事实来源`
  - 给出 1 到 3 个代码锚点、配置锚点或协议锚点

推荐模板：

```md
# 文档标题

状态：`active`
最后验证：`2026-04-03`
适用范围：`<模块/流程>`
单一事实来源：

- `path/to/file_a.py`
- `path/to/file_b.py`
```

维护约定：

- `doc/CURRENT_STATE.md` 可以聚合多个锚点，但仍需明确列出。
- 如果文档和代码冲突，优先修文档或归档旧文档，不保留双版本说法。
- 元信息头缺失时，默认视为需要复核，不应直接作为当前行为依据。
