# develop_doc

本目录存放 SPICEUnion 的长期开发文档。文档按编号目录分层，编号同时表示默认阅读顺序。

开发文档只服务四件事：

- 说明当前事实；
- 说明当前架构；
- 说明下一步施工；
- 保留阶段、专题和遗留判断的上下文。

不要把临时想法、实验流水账或重复事实散写到多篇文档里。

## 阅读顺序

首次接手项目时：

1. `00_项目总览/01_当前事实状态.md`
2. `00_项目总览/02_架构总览.md`
3. `00_项目总览/03_开发路线图.md`
4. `00_项目总览/00_项目章程.md`

准备动代码或写文档前，通读一遍 `DEVELOP_GUIDE.md`，了解一次功能开发在文档侧的
参与流程（开发前/中/后各要动哪些文档）。

需要追溯阶段背景时，再读 `10_阶段记录/`。

需要查看跨阶段专项时，再读 `20_专题记录/`。

需要查看历史调研、候选方案或暂缓判断时，再读 `90_归档备注/`。

## 事实归属

一个事实只在一个主位置展开。

| 内容类型 | 主位置 | 其他位置怎么处理 |
|---|---|---|
| 当前是否支持、测试数字、fixture、backend 状态 | `00_项目总览/01_当前事实状态.md` | 只引用或摘要 |
| 当前分层、模块关系、执行链路、结果读取链路 | `00_项目总览/02_架构总览.md` | 不维护第二套架构图 |
| 下一步开发、完成定义、暂缓条件 | `00_项目总览/03_开发路线图.md` / 根 `TODO` | 不写成当前事实 |
| 项目定位、长期边界、设计原则 | `00_项目总览/00_项目章程.md` | 不记录阶段流水账 |
| 阶段设计理由、阶段内取舍、阶段收口 | `10_阶段记录/` | 当前事实状态只保留最终事实 |
| 跨阶段专项 | `20_专题记录/` | 若改变主线事实，应同步 L1 文档 |
| 外部调研、候选方案、历史备注 | `90_归档备注/` | 若转为正式决策，应提炼到 L1 / L2 文档 |
| 目录职责、命名规则、稳定入口 | 对应目录 `README.md` | 上级 README 不展开孙级细节 |

判断口诀：

```text
现在态 -> 00_项目总览/01_当前事实状态.md 或 02_架构总览.md
将来态 -> 00_项目总览/03_开发路线图.md 或根 TODO
过去态 -> 10_阶段记录/ 或 90_归档备注/
专项态 -> 20_专题记录/
目录边界 -> 就近 README
```

## 命名规则

- 开发文档目录使用两位数字前缀固定阅读顺序，例如 `00_项目总览`、`10_阶段记录`。
- 同一目录下的正式文档使用两位数字前缀固定顺序，例如 `01_当前事实状态.md`。
- 文件名使用稳定业务语义，不使用 `new`、`final`、`tmp`、`v2` 等阶段性词。
- 阶段文档保留 `M1`、`M2` 这类里程碑标识，并在前面加阅读序号。
- 归档备注也使用编号，避免历史材料继续平铺堆积。

## 更新规则

- 改变当前能力、验证结果、backend 状态或未实现边界时，更新 `00_项目总览/01_当前事实状态.md`。
- 改变目录结构、模块关系、执行链路或结果读取链路时，更新 `00_项目总览/02_架构总览.md`。
- 改变后续施工任务、暂缓项或完成定义时，更新 `00_项目总览/03_开发路线图.md` 和根 `TODO`。
- 改变项目定位、范围边界或长期设计原则时，更新 `00_项目总览/00_项目章程.md`。
- 完成阶段或专题任务后，阶段/专题文档只保留必要背景，不复制 L1 当前事实总账。
- 旧结论如果已经被当前代码或 L1 文档覆盖，应删除、归档或明确标注，不保留两套相互竞争的说法。
- README 类文档只写目录职责、命名规则、稳定入口和长期约定，不记录 TODO、实验流水账或临时命令。

## 大改流程

大改/重构级变更的文档参与流程不在此重复维护，请按 `DEVELOP_GUIDE.md` 的步骤执行。
最简检查顺序：根 `TODO` 写分步方案 → 按方案修改 → 更新受影响的 L1 文档与目录
README → 运行必要检查 → 清理根 `TODO` → 本地提交。

## 草案规范

尚未落地、但需要先讨论清楚的方向，可以新增草案文档。草案应优先放在相关层级目录中，
例如用户工作流 API 可放在 `20_专题记录/`。

草案顶部建议包含：

```text
状态：`draft`
最后验证：`YYYY-MM-DD`
适用范围：`<模块/流程/阶段>`
单一事实来源：

- `<落地后对应的代码或测试锚点>`
```

草案只表达目标、边界、方案和完成定义。落地前不得写进当前事实或当前架构；落地后应提炼进
L1 文档，并删除或归档草案中的过期内容。
