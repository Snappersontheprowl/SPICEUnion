# develop_doc

本目录只保留 SPICEUnion 开发过程中的长期有效文档。

开发文档的目标不是记录所有想法，而是让维护者能快速回答四个问题：

- 当前事实是什么；
- 当前架构是什么；
- 下一步做什么；
- 某个阶段或专题为什么这样设计。

文档分工采用：

```text
事实 / 章程 / 路线 / 阶段 / 专题 / 备注 / 表达
```

## 阅读顺序

首次了解项目开发状态时，建议按以下顺序阅读：

1. `当前事实状态.md`：确认当前已实现能力、验证结果和明确边界。
2. `架构总览.md`：理解当前稳定架构、模块关系和主链路。
3. `开发路线图.md`：确认下一步施工任务和完成定义。
4. `M1.md` / `M2.md` / `M3.md` / `M4.md`：按需查看阶段背景、设计理由和历史决策。
5. `OrderedConcurrentPool开发路线图.md` / `遗留备注/`：按专题或遗留问题查阅。

不建议从阶段文档直接判断项目现状；当前事实以 `当前事实状态.md` 为准。

## 文档分层

开发文档按“当前事实优先、历史解释靠后”的方式分层。

| 层级 | 类型 | 作用 | 更新频率 | 典型文件 |
|---|---|---|---|---|
| L0 | 入口地图 | 说明开发文档怎么读、怎么维护 | 低 | `README.md` |
| L1 | 当前事实 | 聚合当前实现、验证数字、能力边界 | 中 | `当前事实状态.md` |
| L1 | 当前架构 | 表达已经落地并稳定的模块关系 | 中 | `架构总览.md` |
| L1 | 用户/项目章程 | 说明项目定位、范围和长期原则 | 低 | `CPP版本开发计划书.md` |
| L2 | 施工路线 | 管理下一步任务、完成定义、暂缓条件 | 中 | `开发路线图.md` |
| L2 | 阶段文档 | 保存某一阶段的设计背景、阶段契约和收口说明 | 中低 | `M1.md`、`M2.md`、`M3.md`、`M4.md` |
| L2 | 专题文档 | 管理跨阶段专项或外部依赖专项 | 中低 | `OrderedConcurrentPool开发路线图.md` |
| L3 | 遗留备注 | 保存调研过程、候选方案、暂缓判断和历史上下文 | 低 | `遗留备注/` |

规则：

- L1 文档是当前判断入口；L2 / L3 文档不能覆盖 L1 的当前事实。
- 阶段文档可以记录阶段内“当时如何想”，但如果与当前代码或 `当前事实状态.md` 冲突，应以当前事实为准。
- `架构总览.md` 只画已经落地的稳定结构；未实现方案进入 `开发路线图.md` 或草案文档。
- `开发路线图.md` 只管理未完成或下一步工作，不复制当前事实细节。

## 文档分工

| 类型 | 文件 | 职责 |
|---|---|---|
| 事实 | `当前事实状态.md` | 当前已实现能力、验证结果、fixture、backend 状态与未实现边界的唯一总账。测试数字、能力边界和“当前是否支持”优先写入此文件。 |
| 架构 | `架构总览.md` | 总体分层、执行链路、结果读取链路与模块责任图。只表达当前已落地结构，不提前画草案。 |

| 路线 | `开发路线图.md` | 下一步施工任务、进入条件、完成定义、暂缓条件和验证矩阵。只写未来施工，不重复当前事实总账。 |

| 阶段 | `M3.md` | M3 多仿真器接入、结果语义对照、当前边界和后续推进选项的阶段责任文档。 |
| 阶段 | `M4.md` | M4 pybind11 与 C ABI 接入状态、分阶段计划和后续评估项的阶段责任文档。 |
| 专题 | `OrderedConcurrentPool开发路线图.md` | OrderedConcurrentPool 独立化专项的边界、装配关系和当前状态 |
| 备注 | `遗留备注/` | 外部调研、遗留判断、候选方案和暂缓问题；不作为当前事实状态或路线图的替代 |
| 表达 | `../resume/` | 简历、面试、汇报口径（如 `简历亮点解析.md`、事件笔记）；不作为开发事实源；本地私有，不入库 |

## 事实归属规则

写文档前先判断内容属于哪一类。

| 内容类型 | 主位置 | 其他位置怎么写 |
|---|---|---|
| 当前支持的 API、backend、格式、fixture、测试数字 | `当前事实状态.md` | 其他文档只引用或摘要，不复制完整清单 |
| 当前模块关系、执行链路、结果读取链路 | `架构总览.md` | 阶段文档可解释来源，但不维护第二套图 |
| 下一步任务、完成定义、暂缓条件 | `开发路线图.md` / 根 `TODO` | 当前事实文档只记录“未实现边界” |
| 某阶段设计理由、阶段内取舍、收口说明 | `M*.md` | 当前事实状态只提炼最终事实 |
| 外部库调研、候选方案、暂不采纳原因 | `遗留备注/` 或专题文档 | 若转为正式决策，应提炼进对应 L1 / L2 文档 |
| 目录职责、命名规则、稳定入口 | 对应目录 `README.md` | 上级 README 不展开孙级细节 |
| 简历、面试、汇报材料 | `doc/resume/` | 不作为开发事实来源 |

判断口诀：

```text
现在态 -> 当前事实状态 / 架构总览
将来态 -> 开发路线图 / TODO
过去态 -> 阶段文档 / 遗留备注
目录边界 -> 就近 README
```

## 维护规则

- 一个事实只在一个主位置展开；当前事实以 `当前事实状态.md` 为准。
- `架构总览.md` 只保存当前稳定架构关系；若目录、阶段职责、执行链路或结果读取链路变化，应同步更新。
- `CPP版本开发计划书.md` 不记录测试结果流水账，只保留项目章程和阶段摘要。
- `开发路线图.md` 不重复事实细节，只记录后续施工路线和完成定义。
- `M1.md` 是 M1 阶段的责任文档；Spectre 执行层、Evaluator、SimulatorSession、TaskResult 与 batch 契约优先写入该文件。
- `M2.md` 是 M2 阶段的责任文档；ResultIR、结果读取、libpsf backend、fixture 与结果层暂缓项优先写入该文件。
- `M3.md` 是 M3 阶段的责任文档；M3 相关现状、待办和推进选项优先写入该文件。
- `M4.md` 是 M4 阶段的责任文档；M4 相关基线、问题和开发切分优先写入该文件。
- 专题文档只覆盖对应专题，不反向替代主计划或主路线。
- `遗留备注/` 只保存暂不进入主线文档的判断过程、外部链接和候选方案；若备注转为正式决策，应提炼后同步到对应主文档。
- 简历材料必须引用已验证事实，不得把目标、计划或未实测性能写成完成结果。
- 新增开发文档前，优先判断是否能合并到现有分类中。
- 阶段文档、专题文档和备注中的旧结论如果已经被代码或当前事实覆盖，应删除、归档或明确标注，不保留两套相互竞争的说法。
- README 类文档只写目录职责、命名规则、稳定入口和长期约定；不记录 TODO、实验流水账或临时命令。
- 大改或重构级变更开始前，先在根 `TODO` 写分步骤方案；完成后清理根 `TODO`，并同步更新受影响的当前事实、架构、路线和目录 README。

## 更新流程

常规代码或文档变更按以下顺序收口：

1. 判断变更是否改变公开行为、目录结构、入口命令、配置开关或验证结果。
2. 若改变当前能力或验证结果，更新 `当前事实状态.md`。
3. 若改变模块关系、目录职责或主链路，更新 `架构总览.md` 和对应目录 README。
4. 若改变后续计划或暂缓边界，更新 `开发路线图.md` 和根 `TODO`。
5. 若完成某阶段或专题任务，只在阶段/专题文档中保留必要背景，不重复 L1 当前事实。

新增文档前必须先问：

- 能否合并到现有 `当前事实状态.md`、`架构总览.md`、`开发路线图.md` 或阶段文档；
- 是否只是临时调研或候选方案，若是则放入 `遗留备注/`；
- 是否需要成为长期专题，若是则在本文 `文档分工` 表中登记。

## 专题草案规范

对尚未落地、但需要先讨论清楚的方向，可以新增草案文档。草案文件名应使用稳定业务语义，
例如 `用户工作流API设计.md`，不要使用 `new`、`final`、`tmp`、`v2` 等阶段性词。

草案顶部建议包含：

```text
状态：`draft`
最后验证：`YYYY-MM-DD`
适用范围：`<模块/流程/阶段>`
单一事实来源：

- `<落地后对应的代码或测试锚点>`
```

草案只能表达目标、边界、方案和完成定义。落地前不得把草案内容写进
`当前事实状态.md` 或 `架构总览.md` 的当前事实部分；落地后应提炼进 L1 文档，并删除或归档
草案中的过期内容。
