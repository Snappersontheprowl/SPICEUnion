# M4 C ABI 与 pybind11 接入草案

更新时间：2026-08-12

本文负责 SPICEUnion M4 阶段的开发规划。当前结论是：

```text
可以开始 M4 设计；
不建议直接进入 C ABI / pybind11 正式实现。
```

M4 的第一步应是接口范围、所有权规则、Python API 形态和测试策略的确认。确认完成后，再进入最小 pybind11 绑定或 C ABI 实现。

## 1. M4 目标

M4 的目标是让 SPICEUnion 的 C++ 能力以稳定、可测试、低负担的方式暴露给外部调用方。

候选外部调用方：

- Python；
- C；
- 未来其他语言或工具链。

当前更现实的第一调用方是 Python，因为项目来源于既有 Python 版
`spectre_interactive` 工作流。

## 2. 当前判断

当前不建议直接写正式 C ABI 或完整 pybind11 binding，原因：

- C++ API 还在 M3 收敛判断点；
- `EvaluatorOptions`、输入入口、ResultIR 是否扩展仍未完全冻结；
- C ABI 需要先明确内存所有权、数组生命周期、字符串释放和错误语义；
- pybind11 如果过早绑定完整 `Evaluator`，后续 C++ API 变化会造成重复返工；
- Python 第一版 API 形态尚未确认。

因此 M4 当前应从：

```text
M4.0 接入草案
```

开始，而不是直接进入：

```text
M4.1 binding 实现
```

## 3. M4 范围

### 3.1 范围内

- pybind11 是否先于 C ABI 的决策；
- 第一版 Python API 范围；
- C++ 类型到 Python 类型的映射；
- C ABI ownership 规则草案；
- Python package / import smoke test 策略；
- binding 层测试策略；
- 是否绑定 `Evaluator` 的进入条件。

### 3.2 范围外

- 不在 M4.0 直接实现完整 binding；
- 不把所有 C++ 类型无差别暴露给 Python；
- 不为了绑定层修改 C++ core 的主线语义；
- 不把 C ABI 当作普通 wrapper 随手写；
- 不在没有真实需求前承诺 MATLAB 或其他语言；
- 不把业务 metric、objective、optimizer 放进 binding。

## 4. 推荐路线

推荐路线：

```text
先 pybind11，后 C ABI。
```

理由：

- Python 是当前最明确的潜在调用方；
- pybind11 能更快验证 C++ API 是否好用；
- C ABI 设计成本更高，且一旦暴露更难修改；
- 当前没有明确 MATLAB / C / 其他语言用户；
- pybind11 第一版可以很小，风险可控。

但这不是最终决定。若用户明确要求跨语言稳定 ABI，则可以改为先做 C ABI。

## 5. 可选方案

### 方案 A：先做 pybind11 最小绑定（推荐）

第一版只绑定结果读取 helper 和少量基础类型。

候选绑定：

- `version()`
- `ResultStatus`
- `ScalarResult`
- `DcSweep`
- `AcResponse`
- `AcDerivedView`
- `TranWaveform`
- `read_dc_value()`
- `read_ac_response()`
- `read_tran_waveform()`
- `derive_ac_view()`
- `calculate_ugbw_and_phase_margin()`
- `calculate_settling_time()`

暂不绑定：

- `Evaluator`
- `SimulatorSession`
- `SpectreSession`
- `NgspiceSession`
- `SessionFactory`
- `OrderedConcurrentPool`
- C ABI。

优点：

- 工作量小；
- 生命周期简单；
- 能先验证 Python 侧结果读取体验；
- 不过早暴露执行层复杂生命周期。

缺点：

- Python 侧暂时不能直接发起完整 batch 仿真；
- 只能先使用已有 work_dir / fixture / 结果目录。

### 方案 B：pybind11 直接绑定 `Evaluator`

第一版就让 Python 能跑 batch evaluator。

候选绑定：

- `EvaluatorOptions`
- `ParameterState`
- `TaskStatus`
- `TaskResult`
- `make_spectre_evaluator()`
- `make_ngspice_evaluator()`
- `Evaluator.run()`

优点：

- Python 侧更接近原 `GenericEvaluator.run(states, parse_func)` 使用方式；
- 能更早验证执行层端到端体验。

风险：

- 生命周期复杂；
- 外部 EDA 工具依赖更难测；
- `EvaluatorOptions` 若后续变化，Python API 会跟着变；
- session factory 这类 C++ 回调不适合第一版直接暴露。

进入条件：

- M3 收敛后确认 `EvaluatorOptions` 和执行入口稳定；
- 明确 Python API 是否允许只支持内置 factory；
- 有 external 测试或 skip 策略。

### 方案 C：先设计并实现 C ABI

先建立稳定 C ABI，再让 Python 或其他语言通过 C ABI 调用。

候选内容：

- `su_status_t`
- `su_string_t`
- `su_double_array_t`
- opaque handle；
- create / destroy；
- result free；
- error message ownership。

优点：

- 适合长期跨语言；
- 对 ABI 边界控制最明确；
- 后续 MATLAB / C / 其他 FFI 更容易接入。

风险：

- 初始设计成本最高；
- 需要非常明确的内存所有权；
- 会引入大量桥接结构；
- 当前 C++ API 未完全冻结时容易返工。

当前判断：

```text
暂不推荐作为第一实现步骤。
```

产出：

- 用户确认是否暂缓 C ABI；
- 用户确认 Python 返回对象形态；
- 用户确认是否绑定 evaluator。

### M4.1 pybind11 最小结果读取绑定

进入条件：

- M4.0 决策完成；
- pybind11 被确认优先于 C ABI；
- 第一版只绑定结果读取 helper。

建议产出：

```text
bindings/python/

  spiceunion_py.cpp
```

或：

```text

  CMakeLists.txt
  spiceunion_py.cpp
  tests/
```

完成定义：

- 可构建 Python extension；
- `python -c "import spiceunion"` 通过；
- 能读取至少一个已提交 fixture；
- CTest 或 pytest 覆盖 import smoke test；
- 默认构建不强制启用 Python binding；
- README 与 `当前事实状态.md` 更新。

### M4.2 Python API 稳定化

目标：

- 让 Python 返回值形态稳定；
- 补充基础文档和示例；
- 明确错误转换规则。

完成定义：

- Python API 有最小示例；
- 失败状态不会伪装成 `None` 或 `0.0`；
- 读取失败有明确 status / message；
- 不暴露 libpsf 类型。

### M4.3 执行层 binding 评估

目标：

- 判断是否绑定 `Evaluator`；
- 判断是否先提供更窄的执行入口；
- 判断 Spectre / Ngspice external 测试策略。

可选方向：

1. 绑定现有 `Evaluator`；
2. 提供更窄的 Python 运行函数；
3. 暂不绑定执行层，只保留结果读取 binding。

### M4.4 C ABI 草案或实现

进入条件：

- 明确存在 Python 之外的调用方；
- 或者项目需要稳定二进制 ABI；
- 或者用户明确要求 C ABI 优先。

当前默认：

```text
C ABI 暂缓，只维护 ownership 草案。
```

## 7. Python 返回值形态选项

### 选项 A：Python class / dataclass 风格（推荐）

示例：

```python
response = spiceunion.read_ac_response(result_dir, "vout", "ac.ac")
response.frequency_hz
response.real
response.imag
```

优点：

- 结构清楚；
- 接近 C++ ResultIR；
- 文档容易写；
- 后续可加方法。

缺点：

- binding 代码稍多。

### 选项 B：dict

示例：

```python
response = {
    "status": "ok",
    "frequency_hz": [...],
    "real": [...],
    "imag": [...],
}
```

优点：

- Python 端简单；
- 无需设计太多类。

缺点：

- 类型弱；
- 字段名错误不易提前发现；
- 长期 API 边界松散。

### 选项 C：numpy array

示例：

```python
frequency, real, imag = spiceunion.read_ac_response(...)
```

优点：

- 适合数值计算；
- 对大波形更高效。

缺点：

- 引入 numpy 依赖；
- packaging 更复杂；
- 第一版不必要。

当前推荐：

```text
先 Python class / dataclass 风格；
暂不引入 numpy。
```

## 8. C ABI ownership 草案问题

如果进入 C ABI，必须先回答：

- 字符串由谁分配？
- 调用方如何释放字符串？
- double 数组由谁分配？
- result struct 是否固定布局？
- 是否使用 opaque handle？
- error message 生命周期如何管理？
- evaluator handle 如何 create / destroy？
- 是否允许跨线程调用同一个 handle？
- C ABI 是否暴露 ResultIR？
- C ABI 是否暴露 `Evaluator`？
- C ABI 是否暴露 Spectre / Ngspice backend？

建议原则：

- C ABI 使用 opaque handle 管理复杂对象；
- 所有由 SPICEUnion 分配的内存必须由 SPICEUnion 提供释放函数；
- C ABI 不直接暴露 C++ STL 类型；
- C ABI 不暴露第三方库类型；
- C ABI 第一版只做最小稳定子集。

## 9. 测试策略

### 9.1 pybind11 测试

建议覆盖：

- import smoke test；
- `version()`；
- 一个 scalar fixture；
- 一个 AC fixture；
- 一个 TRAN fixture；
- 一个失败读取 case。

测试入口可选：

- CTest 调用 Python；
- pytest；
- 两者组合。

当前推荐：

```text
先用 CTest 调 Python smoke test，减少依赖。
```

### 9.2 C ABI 测试

若进入 C ABI，至少需要：

- C smoke test；
- create / destroy；
- string / array free；
- failure result；
- ASan 下无泄漏。

## 10. CMake 开关建议

建议新增可选开关：

```cmake
SPICEUNION_BUILD_PYTHON_BINDINGS
SPICEUNION_BUILD_C_API
```

默认：

```cmake
SPICEUNION_BUILD_PYTHON_BINDINGS=OFF
SPICEUNION_BUILD_C_API=OFF
```

原因：

- 默认构建继续保持纯 C++；
- 不强制用户安装 Python / pybind11；
- binding 层可以独立验证。
