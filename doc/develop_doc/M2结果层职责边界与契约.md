# M2 结果层职责边界与契约

时间：2026-08-03

## 1. 背景

SPICEUnion 已完成 M1.3，执行层已经可以把一批参数状态派发给真实
Spectre interactive worker，并按输入顺序返回每个任务的执行状态和工作目录。

M2 开始进入“仿真结果层”。这一层很容易失控：如果边界不清，底层库会逐渐变成同时负责
执行仿真、解释电路指标、定义优化目标、管理实验流程的大而全脚本集合。

M2 的设计依据是：

- `~/my_lab/projects/spectre_materials/doc/仿真自动化职责边界笔记.md`
- 当前 Python `task_library.py` 暴露过的通用结果读取经验
- SPICEUnion 作为 C++ 基础设施库的长期 API 稳定性需求

Python 版是重要参考，但不是兼容枷锁。M2 不为了强行复刻 Python 返回值而牺牲 C++ API
的类型安全、错误语义和扩展性。

## 2. M2 的一句话目标

M2 的目标是：

```text
提供覆盖当前已知需求的通用仿真结果读取原语和最小 ResultIR；
SPICEUnion 只表达仿真产物本身，不表达项目业务指标；
失败语义必须清晰、可测试，并能支撑后续 C ABI / Python binding 收敛。
```

## 3. 职责边界

### 3.1 M2 应该负责

M2 可以进入 SPICEUnion 的能力：

- 定位 worker 目录下的 `.raw` 结果目录。
- 读取 `dcOp.dc` 中的单个工作点标量。
- 读取 `ac.ac` 中的 frequency axis 与复数响应。
- 提供 magnitude / phase 这类通用 AC 派生视图。
- 基于 AC 曲线计算 UGBW / phase margin 这类通用数学量。
- 读取 `tran.tran` 中的 time axis 与 waveform。
- 基于 waveform 计算 settling time 这类通用数学量。
- 读取 legacy sensitivity 结果并整理为结构化条目。
- 对缺失目录、缺失文件、缺失 signal、解析失败给出明确状态。
- 为上述能力建立 fixture 与单元测试。

### 3.2 M2 不应该负责

M2 不进入 SPICEUnion 的能力：

- 某个电路的业务指标定义，例如 AMP 的 VOS。
- 某个项目的 spec / pass-fail 规则。
- objective、constraint、penalty、yield score。
- 优化器策略或设计空间采样。
- PDK 内容管理。
- 实验编排、数据库写入、报告生成。
- 根据项目业务目标决定是否重试仿真。
- 完整网表语法 IR。
- 完整覆盖所有 PSF 方言。

判断标准：

```text
如果一个逻辑换到另一个项目仍然成立，它可能属于 SPICEUnion。
如果一个逻辑依赖具体电路、signal 命名、spec 或优化目标，它属于上层项目。
```

## 4. Python 版的定位

Python `task_library.py` 提供了有价值的历史经验：

- 它说明当前项目真实使用过哪些结果读取能力。
- 它可以帮助选择 M2 的最小功能集合。
- 它可以提供 fixture 生成方式和数值参考。

但 M2 不承诺逐字节、逐返回值兼容 Python helper。

尤其是 Python 版中的这些宽松行为，不应直接污染 C++ core API：

- 读取失败返回 `0.0`。
- 曲线读取失败返回空数组。
- sensitivity 读取失败返回 `None`。
- 捕获所有异常并吞掉失败原因。

C++ core 应优先表达真实状态。未来如果需要 Python 兼容层，可以在 binding 层把明确错误状态
映射成 Python 习惯的 `0.0`、空数组或 `None`。

## 5. 最小 ResultIR

M2 的 ResultIR 只表达仿真结果本身，不表达业务意义。

建议最小类型：

```text
ResultDirectory
ScalarResult
AcResponse
TranWaveform
SensitivityEntry
```

建议字段：

```cpp
enum class ResultStatus {
  kOk,
  kDirectoryNotFound,
  kFileNotFound,
  kSignalNotFound,
  kUnsupportedFormat,
  kParseError,
  kInvalidInput,
};

struct ResultError {
  ResultStatus status;
  std::string message;
};

struct ScalarResult {
  std::string signal;
  double value;
};

struct AcResponse {
  std::string signal;
  std::vector<double> frequency_hz;
  std::vector<double> real;
  std::vector<double> imag;
};

struct AcDerivedView {
  std::vector<double> frequency_hz;
  std::vector<double> magnitude_db;
  std::vector<double> phase_deg;
};

struct TranWaveform {
  std::string signal;
  std::vector<double> time_s;
  std::vector<double> value;
};

struct SensitivityEntry {
  std::string key;
  std::string node;
  std::string parameter;
  double sensitivity;
  double parameter_value;
};
```

其中 `AcResponse` 建议保留 `real` / `imag`，因为这是更接近仿真原始结果的表达；
`magnitude_db` / `phase_deg` 可以作为派生 view 或 helper 结果。

不要在 ResultIR 中加入：

```text
BandgapSpec
VosObjective
YieldScore
AmpSettlingPassFail
PenaltyResult
```

这些属于上层项目。

## 6. 错误语义

M2 的核心原则：

```text
核心 API 不用 0.0 表示失败。
```

建议使用显式状态对象，例如：

```cpp
template <typename T>
struct Result {
  ResultStatus status;
  T value;
  std::string error_message;
};
```

或者在不引入模板的情况下，为每类读取结果定义带状态返回值。

最低要求：

- 成功和失败必须可区分。
- 真实数值 `0.0` 不能和读取失败混淆。
- 缺文件、缺 signal、格式不支持、解析失败应尽量区分。
- 错误信息用于诊断，不应承载业务决策。
- Python 兼容语义只允许在 binding / wrapper 层处理。

## 7. 建议公开 API 切分

建议新增两个公开头文件：

```text
include/su/result.hpp
include/su/result_reader.hpp
```

职责：

- `result.hpp`：定义 ResultIR、ResultStatus、ResultError、通用结果容器。
- `result_reader.hpp`：定义通用读取和数学 helper 的 C++ API。

实现位置：

```text
src/parse/result_reader.cpp
src/parse/result_math.cpp
```

如果后续需要 PSF 专用内部实现，可放在：

```text
src/parse/psf_reader.hpp
src/parse/psf_reader.cpp
```

`psf_reader.hpp` 初期建议作为内部头文件放在 `src/parse/` 下，除非已经准备把 PSF
格式细节承诺为公开 API。

## 8. 建议实施顺序

### M2.1 ResultIR 与 API 骨架

目标：

- 新增 `include/su/result.hpp`。
- 新增 `include/su/result_reader.hpp`。
- 定义 `ResultStatus`、错误语义、最小 ResultIR。
- 写纯类型与边界测试。

验收：

- 头文件可被外部 target include。
- 类型不包含业务指标语义。
- README 说明职责边界。

### M2.2 纯路径与纯数学 helper

目标：

- 实现 `.raw` 结果目录定位。
- 实现 AC magnitude / phase 计算。
- 实现 UGBW / phase margin 计算。
- 实现 waveform settling time 计算。

这些能力不依赖真实 PSF parser，适合先落地。

验收：

- 使用人工构造数组单测。
- 覆盖边界输入：空数组、长度不一致、无 0 dB crossing、目标值为 0 等。
- 失败语义清楚。

### M2.3 最小文件读取能力

目标：

- 实现覆盖当前 fixture 的 `dcOp.dc` 标量读取。
- 实现覆盖当前 fixture 的 `ac.ac` 复数响应读取。
- 实现覆盖当前 fixture 的 `tran.tran` waveform 读取。
- 实现 legacy sensitivity 读取。

验收：

- 有固定 fixture。
- 与可信参考结果在数值容差内一致。
- 解析失败不会被伪装成合法数值。

### M2.4 参考对照与回归测试

目标：

- Python `task_library.py` 只作为参考实现或 fixture 生成器。
- 对照测试关注数值语义，而不是复刻 Python 的失败返回习惯。
- 明确哪些差异是 C++ API 的有意改进。

验收：

- 每个 helper 都有正常路径测试和失败路径测试。
- 文档记录 Python helper 与 C++ helper 的语义差异。

### M2.5 C ABI 草案回看

ResultIR 稳定后再回看 C ABI。

原因：

- C ABI 比 C++ API 更难修改。
- array / string ownership 依赖最终 ResultIR 形状。
- 过早写 C ABI 容易在 M2 内部类型变化时返工。

M2 阶段只需要保证 C++ 设计不会明显阻塞未来 C ABI。

## 9. 测试策略

测试分三层：

### 9.1 类型与数学单测

不依赖 Spectre，不依赖 fixture：

- ResultIR 类型可构造、可移动。
- AC magnitude / phase 计算正确。
- UGBW / PM 插值正确。
- settling time 计算正确。
- 错误输入返回明确状态。

### 9.2 fixture 文件读取测试

依赖小型固定结果文件：

- `.raw` 目录定位。
- dc 单信号读取。
- ac 曲线读取。
- tran waveform 读取。
- sensitivity 条目读取。

fixture 应尽量小。如果真实 PSF 文件过大，不直接提交完整大文件；优先提供生成脚本或小型裁剪样例。

### 9.3 参考实现对照测试

Python 版可以用来生成参考数值，但不是强制兼容标准。

对照测试应记录：

- 输入 fixture。
- 参考数值来源。
- 数值容差。
- C++ 与 Python 在失败语义上的有意差异。

## 10. 完成定义

M2 完成时应满足：

- 最小 ResultIR 已定义并有公开头文件。
- 通用读取 helper 与数学 helper 已实现。
- 正常路径与失败路径都有测试。
- fixture 和参考数值来源可复现。
- 文档明确说明 SPICEUnion 不承载业务指标。
- 未完成的完整 PSF parser、Python binding、C ABI 稳定化仍留在后续阶段。

## 11. 开发前检查清单

每加入一个结果层功能前，先问：

- 它读取的是仿真产物，还是解释业务含义？
- 它是否依赖某个具体电路的 signal 命名？
- 它是否定义了 objective、penalty 或 pass/fail？
- 换一个项目，它还成立吗？
- 它是否需要进入 C++ core，还是应该留在上层 parse_func？
- 它是否会让未来 C ABI 难以表达？
- 它有没有测试 fixture 或人工构造输入？

默认策略：

```text
通用读取能力可以进入 SPICEUnion。
项目业务解释留在外部项目。
没有明确使用者的结果类型推迟。
```
