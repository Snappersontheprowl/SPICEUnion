## 结论

Ngspice 当前没有实现常驻会话，**不是能力缺失，而是工程取舍**：

1. 每次 `ngspice -b` 冷启动 + 极小仿真的实测开销仅约 **21 ms**，典型的模拟仿真
   时长远大于此，会话复用的收益有限；
2. batch 一进程一 job 的状态最干净，避免 `reset`/`alter`/参数作用域残留带来的
   不可解释结果；
3. 上游确实提供常驻能力（`-i` 交互、`-p` 管道、`-s` server 模式，以及
   libngspice 嵌入式 API），所以未来若需要，是可以做的（见“重新评估触发条件”）。

## 上游能力事实（本机 `ngspice -h` 实测，2026-10-05）

```text
-i, --interactive   交互式 REPL（可 source/alter/run/reset 复用同一进程）
-p, --pipe          I/O 管道模式（适合被上层程序驱动）
-s, --server        server 模式（供外部客户端调用）
-a, --autorun       加载网表后自动运行
-r, --rawfile=FILE  指定 raw 输出文件
```

- 上游还提供 **libngspice**（嵌入式 C API，如 `ngSpice_Init` / `ngSpice_Command`）；
- 本机当前基线（`/usr/local/bin/ngspice`，v27 源码构建）**未提供** libngspice：
  `ldconfig -p | grep ngspice` 无结果，`/usr/local/lib*` 下也没有对应共享库；
- conda-forge 的 ngspice 41 环境同样以可执行文件为主（本机验证范围）。

## SPICEUnion 当前实现

- `NgspiceSession::start()`：仅创建 worker 目录并解析 ngspice 可执行文件；
- `NgspiceSession::run()`：每个 job 新起 `ngspice -b` 子进程（`fork`），完成后读取
  `wrdata` 文本；
- `SpectreSession`：长驻 interactive 进程（SKILL handshake 后多次 `sclRun`），
  其产物目录在启动时由 `-o` 绑定，无法按 job 切换（专题 06 实验 A/B）。

## 不采用常驻的主要理由

| 维度 | batch（当前） | 常驻/嵌入（候选） |
|---|---|---|
| 单 job 开销 | 约 21 ms 启动（实测） | 理论上更低，但需实测净收益 |
| 状态正确性 | 进程级隔离，天然无残留 | 依赖 `reset`/`alter` 语义与实现纪律 |
| 完成判定 | 进程退出 + 产物文件 | 提示符/协议解析，输出交错需处理 |
| 崩溃与超时 | kill 单进程即可 | 需重启会话与恢复逻辑（类似 Spectre 的 restart） |
| 线程安全 | 多进程天然并行 | libngspice 非线程安全，需多实例或串行化 |
| 分发成本 | 只需已安装的 ngspice 可执行文件 | 需链接共享库/ABI 兼容，或解析协议 |
| 扩展方式 | — | 可作为 `SimulatorSession` 的新 backend 变体接入 |

## 重新评估的触发条件

满足以下**任一**条件时再启动评估（避免凭感觉优化）：

1. 出现大量“极短 job”（单 job 仿真时间与 21 ms 启动同量级），启动开销占比可测；
2. 批量吞吐成为明确瓶颈，且 `default`/`external` 预设的实测数据支持（记录机器、
   case 数、解析/仿真时间比）；
3. 上游出现稳定的 server/pipe 用例与参考实现，协议复杂度显著下降。

## 若重新评估：验证步骤（先探针、后实现）

1. 写手动探针（放 `tests/manual/`）：分别用 `-s` / `-p` 驱动，测每 job 净开销；
2. 验证能否为每次 run 切换输出目录（参照专题 06 实验 A/B 的方法）；
   - 可切换 → 支持“每 job 子目录”，与专题 07 的 P0 一致；
   - 不可切换 → 复用既有结论：每 job 快照或 worker 内即时提取；
3. 验证状态语义：连续 run 的 `reset`/`alter`/参数作用域是否完全隔离（构造可判别
   的用例，断言第 N 次结果只受第 N 次参数影响）；
4. 只有三项都通过，才考虑实现新的常驻 backend 变体，并同步事实状态与架构文档。
