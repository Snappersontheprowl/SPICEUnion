# M3 多仿真器接入与结果语义收敛文档

更新时间：2026-08-12

本文负责 SPICEUnion M3 阶段的现状总结、待办边界和后续推进选项。

当前结论：

```text
M3.0-M3.4 已完成基础闭环；
M3.5 OrderedConcurrentPool 独立化已完成；
M3 是否继续收敛，需要用户决定。
```

M3 当前不是“完全没做完”，而是已经具备第二仿真器 Ngspice 的基础能力。剩余问题主要是是否继续补齐跨 backend 语义对照，以及是否进入 MOS I-V / gm/Id 这类更复杂结果场景。

## 1. M3 目标

M3 的目标是验证 SPICEUnion 是否能从单一 Spectre backend 扩展到至少两个真实仿真器 backend，并保持统一的执行语义与结果读取语义。

M3 关注：

- 第二仿真器 Ngspice 接入；
- batch 执行语义；
- AC / TRAN / DC sweep 基础结果语义；
- Spectre 与 Ngspice 的同类场景对照；
- `Evaluator`、`TaskResult`、`ResultIR` 是否足够支撑多 backend。

M3 不关注：

- 完整 netlist IR；
- 通用 netlist 生成 DSL；
- MOS gm/Id lookup table；
- optimizer；
- Hspice / Xyce；
- Python binding；
- C ABI。

## 2. 当前已完成事实

### 2.1 Spectre backend

已具备：

- `spectre +interactive` 启动；
- SKILL handshake；
- circuit handle 初始化；
- 参数写入；
- `(sclRun "all")`；
- completion 判断；
- graceful / force stop；
- evaluator multi-worker batch；
- PSF `dcOp.dc` scalar fixture；
- PSF `ac.ac` / `stb.stb` swept complex fixture；
- 普通 PSF transient fixture；
- Spectre RC low-pass AC fixture；
- Spectre RC charging TRAN fixture。

当前边界：

- Spectre 23.1 PSFXL transient fixture 当前明确返回 `kUnsupportedFormat`；
- legacy sensitivity 读取未实现；
- Spectre 侧 DC sweep 尚未与 Ngspice `DcSweep` 做同类语义对照。

### 2.2 Ngspice backend

已具备：

- `ngspice -b` batch mode；
- 每个 worker 独立工作目录；
- 内置任务 netlist 渲染；
- ngspice stdout / 输出文件读取；
- failure 通过 `TaskResult` 返回；
- `make_ngspice_session_factory(task)`；
- `make_ngspice_evaluator(options, task)`。

当前 `NgspiceBuiltinTask`：

| 任务 | 输出文件 | 输出格式 | ResultIR |
|---|---|---|---|
| `kRcAc` | `rc_ac.out` | 三列 `frequency real imag` | `AcResponse` |
| `kRcTran` | `rc_tran.out` | 两列 `time value` | `TranWaveform` |
| `kResistorDividerDc` | `resistor_divider_dc.out` | 两列 `sweep_value value` | `DcSweep` |

当前边界：

- 不是任意 Ngspice netlist 执行器；
- 只支持内置教学级 batch 任务；
- 尚未实现 `.op` operating point；
- 尚未进入 MOS I-V / gm/Id。

### 2.3 ResultIR 与结果读取

M3 相关已用到：

| ResultIR | 当前状态 |
|---|---|
| `ScalarResult` | Spectre DC operating point scalar 已覆盖 |
| `DcSweep` | Ngspice resistor divider DC sweep 已覆盖 |
| `AcResponse` | Spectre / Ngspice RC AC 已覆盖 |
| `AcDerivedView` | AC magnitude / phase 派生已覆盖 |
| `TranWaveform` | Spectre / Ngspice RC TRAN 已覆盖 |
| `ReadResult<T>` | 显式 status / message 失败语义已覆盖 |

当前 `DcSweep` 只表达：

```text
单 sweep axis、单 signal 实数响应
```

它尚未表达：

- 多条曲线；
- family curve；
- 多维 sweep；
- MOS I-V 曲线族；
- gm/Id lookup table。

### 2.4 Spectre / Ngspice 对照

已完成的同类语义对照：

| 场景 | Spectre | Ngspice | 状态 |
|---|---|---|---|
| RC low-pass AC | 已有 fixture | 已有 external test | 已完成基础对照 |
| RC charging TRAN | 已有 fixture | 已有 external test | 已完成基础对照 |
| resistor divider DC sweep | 未做 Spectre fixture | 已有 external test | 待评估 |

当前判断：

```text
AC / TRAN 已足够证明第二仿真器基础闭环；
DC sweep 只有 Ngspice 侧，尚不足以证明跨 backend DC sweep 语义一致。
```

- `~/my_lab/projects/OrderedConcurrentPool`；
- C++17 header-only；

## 4. M3 后续推进选项

### 选项 A：M3 到此收口，进入 M4

含义：

- 承认 M3 已完成“第二仿真器基础闭环”；
- 不继续补 Spectre DC sweep；
- 不进入 MOS I-V / gm/Id；
- 把剩余事项留在暂缓池；
- 直接进入 M4.1 pybind11 最小结果读取绑定。

适合情况：

- 当前目标是尽快让 C++ 结果读取能力给 Python 使用；
- DC sweep 跨 backend 对照不是近期真实需求；
- 不想让 M3 继续膨胀。

代价：

- `DcSweep` 仍只有 Ngspice 侧真实语义测试；
- Spectre / Ngspice 的 DC sweep 统一性没有被证明。

### 选项 B：做 M3 最小收口后再进入 M4（推荐）

含义：

- 补一个无 PDK 依赖的 Spectre resistor divider DC sweep fixture；
- 验证 Spectre PSF DC sweep 能否映射到现有 `DcSweep`；
- 与 Ngspice `kResistorDividerDc` 复用同类语义检查；
- 不进入 MOS；
- 不扩展 `DcSweep` 结构。

适合情况：

- 希望 M3 的 AC / TRAN / DC 三类基础结果都完成跨 backend 对照；
- 希望 M4 pybind11 暴露 `DcSweep` 时底层语义更踏实；
- 愿意接受一个小型 fixture 与测试补充。

完成定义：

- 新增 Spectre resistor divider DC sweep 源 fixture；
- 固化对应 PSF fixture；
- libpsf 构建能读出 Spectre `DcSweep`；
- Ngspice DC sweep external test 仍通过；
- 共享检查逻辑验证分压比例；
- `当前事实状态.md` 与测试 README 同步更新。

暂缓条件：

- 本机无法生成或确认 Spectre DC sweep PSF；
- libpsf 无法读取该格式；
- fixture 需要引入 PDK 或模型依赖；
- 用户认为 M4 优先级更高。

### 选项 C：进入 MOS I-V / gm/Id 需求评估

含义：

- 开始评估 MOS I-V 是否需要 family curve；
- 判断 `DcSweep` 是否要扩展为多曲线结构；
- 判断 gm/Id 数据是否属于 SPICEUnion core 范围。

适合情况：

- 已经有真实 MOS 模型；
- 已经有明确的 gm/Id 或 I-V 消费者；
- 希望 SPICEUnion 直接服务晶体管表征流程。

当前不推荐直接做，原因：

- 会把 M3 从“仿真器基础设施”推向“器件表征业务”；
- 需要模型、工艺节点、偏置范围和参考结果；
- 很容易诱导提前设计多维 ResultIR；
- gm/Id lookup table 更适合放在上层应用或独立模块，而不是 SPICEUnion core。

若用户选择该方向，需要先提供或确认：

- MOS 模型来源；
- NMOS / PMOS 类型；
- sweep 变量；
- family curve 维度；
- 输出字段；
- 是否需要 gm、gds、ro、ft 等派生量；
- 结果是否进入 SPICEUnion core。

### 选项 D：扩展 EvaluatorOptions 或 netlist template

含义：

- 为多 backend 引入更通用的任务配置；
- 或提供 netlist template 输入接口。

当前不推荐，原因：

- 现有 `ParameterState` 与内置任务枚举仍能支撑当前测试；
- 没有两个 backend 共同提出同类配置需求；
- 过早做会接近完整 request IR 或 DSL；
- 用户已明确偏好“网表、仿真器、执行、读取结果”的简单逻辑，不应为未来功能提前复杂化。

进入条件：

- Spectre 与 Ngspice 两个 backend 都需要同类配置能力；
- 内置任务枚举无法表达真实需求；
- 有明确消费者，而不是架构预想。

## 5. 当前推荐

如果继续推进 M3，我推荐：

```text
只做选项 B：Spectre 侧 resistor divider DC sweep 对照。
```

推荐原因：

- 工作边界小；
- 不引入 MOS 模型；
- 不扩展 ResultIR；
- 能补齐 AC / TRAN / DC 三类基础结果的跨 backend 语义闭环；
- 对后续 M4 pybind11 暴露 `DcSweep` 有帮助。

如果用户希望尽快进入 M4，则可以选择选项 A，直接把 M3 暂缓项留档。
