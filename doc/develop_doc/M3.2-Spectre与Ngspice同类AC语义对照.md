# M3.2 Spectre 与 Ngspice 同类 AC 语义对照

时间：2026-08-06

本文记录 M3.2 的事实状态：在 M3.0 / M3.1 已经让 Ngspice AC / TRAN 进入 ResultIR
之后，补齐 Spectre 侧同类 RC low-pass AC 材料，并验证 Spectre PSF 读取结果与 Ngspice
`wrdata` 结果可以复用同一套 AC 语义检查。

## 当前结论

M3.2 已完成 Spectre / Ngspice 同类 AC 语义对照的第一步。

新增材料：

| 类型 | 路径 | 作用 |
|---|---|---|
| Spectre 源 netlist | `tests/fixtures/spectre/rc_lowpass_ac/input.scs` | 记录可复现输入 |
| Spectre 固化 PSF | `tests/fixtures/psf/spectre_rc_lowpass_ac.raw/ac.ac` | libpsf reader 与 ResultIR 语义测试 |
| 公共测试 helper | `tests/support/rc_semantics.hpp` | RC AC / TRAN 物理语义检查 |
| 语义契约测试 | `tests/simulation_semantics_test.cpp` | Spectre PSF -> `AcResponse` -> RC AC semantic check |

M3.2 的重点不是新增仿真器功能，而是把测试材料和测试架构补齐：源 netlist 与固化结果分开，
backend-specific reader 与 ResultIR semantic contract 分开。

## Spectre RC low-pass AC fixture

源 netlist：

```text
tests/fixtures/spectre/rc_lowpass_ac/input.scs
```

电路：

```text
Vin -- R1 -- out
             |
             C1
             |
             0
```

参数：

| 参数 | 值 |
|---|---:|
| `R` | `1 kΩ` |
| `C` | `1 pF` |
| `Vin` AC magnitude | `1 V` |
| AC sweep | `1 MHz` 到 `10 GHz`，每 decade 100 点 |

理论 -3 dB 频率：

```text
fc = 1 / (2πRC) ≈ 159.154943 MHz
```

生成命令要点：

```bash
spectre tests/fixtures/spectre/rc_lowpass_ac/input.scs \
  -64 \
  -raw spectre_rc_lowpass_ac.raw \
  -format psfbin
```

本机 Spectre 版本：

```text
Spectre 23.1.0.063 64bit
```

生成后的固化结果：

```text
tests/fixtures/psf/spectre_rc_lowpass_ac.raw/ac.ac
```

该结果可由当前 `SPICEUNION_ENABLE_LIBPSF_READER=ON` 下的 `read_ac_response()` 读取，
signal 名称为：

```text
out
```

## tests 架构调整

M3.2 后，fixture 与语义测试的职责如下：

```text
tests/
├── fixtures/
│   ├── spectre/        # 可复现源 netlist
│   └── psf/            # 固化 PSF 结果
├── support/            # 测试 helper，不进入 public API
└── simulation_semantics_test.cpp
```

`tests/support/rc_semantics.hpp` 当前提供：

- `expect_rc_lowpass_ac_semantics(...)`
- `expect_rc_charging_tran_semantics(...)`
- 小型插值 / 搜索 helper

这些 helper 只属于测试层，不进入 `include/su/`。这样可以先用真实样本收敛 ResultIR 语义，
但不急着把“语义契约”产品化成公共 API。

## 当前测试覆盖

Ngspice external AC 测试：

```text
NgspiceSessionExternalTest.RunsRcLowPassAcWhenExternalNgspiceIsEnabled
```

路径：

```text
Ngspice wrdata rc_ac.out
  -> read_ngspice_wrdata_ac_response()
  -> AcResponse
  -> expect_rc_lowpass_ac_semantics()
```

Spectre PSF fixture 语义测试：

```text
RcAcSemanticContractTest.SpectreRcLowpassAcFixtureUsesCommonAcResponseSemantics
```

路径：

```text
Spectre PSF ac.ac
  -> read_ac_response()
  -> AcResponse
  -> expect_rc_lowpass_ac_semantics()
```

也就是说，两个 backend 的原始输出格式不同：

| Backend | 原始输出 | Reader |
|---|---|---|
| Ngspice | `wrdata` 文本三列 | `read_ngspice_wrdata_ac_response()` |
| Spectre | PSF `ac.ac` | `read_ac_response()` |

但进入 `AcResponse` 后，二者复用同一套 RC low-pass AC 语义检查。

## 当前边界

M3.2 仍不做：

- Spectre / Ngspice 同类 TRAN 对照；
- `.dc` sweep ResultIR；
- 完整 netlist IR；
- 通用 simulation request / probe binding；
- 把 `tests/support/rc_semantics.hpp` 升级为 public API。

当前合理结论是：

```text
AcResponse 已经被 Ngspice wrdata 和 Spectre PSF 两条真实路径共同验证。
```

后续如果继续 M3，优先考虑：

- 是否需要 Spectre / Ngspice 同类 TRAN 对照；
- 是否存在真实 `.dc` sweep 消费者；
- 是否有两个 backend 共同需要更高层的 netlist template / output probe 抽象。
