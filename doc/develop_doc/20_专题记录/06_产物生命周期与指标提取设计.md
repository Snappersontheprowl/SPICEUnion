## 1. 背景：已复现的产物覆盖缺陷

当前实现中：

- `SimulatorPool` 为每个 worker 固定分配 `workspace_root/worker_<id>`；
- session 长驻复用该目录（Spectre 启动时 `-o <work_dir>` 固定；Ngspice 每次
  以 trunc 方式写同名输出文件）；
- 批任务返回后，调用方再逐个读取结果。

**实测复现（2026-10-03）**：Ngspice 内置 RC AC 任务，`workers=1`，三个不同电容
（1p / 2p / 4p）：

```text
case0: work_dir=.../worker_0  last_mag=3.979e-03
case1: work_dir=.../worker_0  last_mag=3.979e-03
case2: work_dir=.../worker_0  last_mag=3.979e-03
worker_0/ 下只剩 ngspice.log、rc_ac.cir、rc_ac.out
```

三者目录相同、读数相同（均为最后一个 job 的结果），说明**前序 job 的产物在读取
前已被后续 job 覆盖**。`workers=N` 时每个 worker 只会保留它最后一个 job 的产物。

现有测试未覆盖该场景：契约测试使用 fake session（只验证保序/失败语义），真实
工具端到端只跑了单个 case。

## 2. 问题拆解

三个正交问题，本设计分别处理：

1. **产物隔离**：同一 worker 的连续 job 如何不互相覆盖；
2. **提取时机与位置**：指标在“worker 内、下一个 job 前”提取，还是“批结束后由
   调用方提取”；
3. **提取内容由谁定义**：执行层不定义业务指标，必须由上层声明。

现状补充事实：批结束后由调用方逐个读取 = **解析串行**（worker 已空闲）；Python
绑定仅 `Simulation.run` 释放 GIL，`read_*` 未释放，多线程读取无法并行；reader
实现无共享状态（理论可并发，但无并发测试）。

## 3. 方案一：worker 内即时提取上层指标

**机制**：job 完成后、下一个 job 启动前，在 worker 线程内按声明提取指标，结果随
`TaskResult` 一起返回；原始产物按保留策略处理。

需要的契约：

- `ExtractionSpec`：声明式读取请求（如 `dc: ["vout","idd"]`、
  `ac: ["out"] → ugbw/phase_margin`、`tran: ["out"] → settling_time`）；
- 提取状态与仿真状态分离（`simulation ok` 不等于 `extraction ok`，BINPSF 无
  libpsf、PSFXL 不支持都在此暴露）；
- 原始产物保留策略（默认建议：失败必留；成功可选全留/限量/不留）。

并行度特征：

- 跨 worker 并行（每个 worker 解析自己的 job）；
- 与仿真形成流水线（worker A 解析时 worker B 仍在仿真）；
- 单 worker 内仍串行；不提供“单文件内部并行解析”。

优点：彻底规避覆盖；免去快照拷贝；解析与仿真重叠；大波形可不落盘。

代价与风险：提取声明增加 API 复杂度；解析占用 worker 时间（解析/仿真比高时
吞吐下降）；批量结果常驻内存会放大占用（建议标量/派生指标优先，波形按需）；
需明确与既有 `read_*` 的兼容策略（保留 raw 时可继续用，否则必须走提取结果）。

成本估计：MVP（标量 + AC 派生 + settling time，不含大波形）约 1–2 天。

## 4. 方案二：仿真器原生测量直出

**机制**：由网表声明测量语句，仿真器自己算出指标；SPICEUnion 只做“声明格式 +
解析小文本 + 即时读取”，连波形产物都不需要。

- Ngspice：`.meas`（如 `ugbw WHEN vdb(out)=0`、`tsettle WHEN v(out)=0.9*VDD`），
  结果输出到 stdout/log；
- Spectre：`measure` 语句，结果落在 `.measure`/日志。

实现分档：

- **A. 直通（建议先做）**：用户网表已含合法测量语句；新增
  `ResultFormat::kMeasure` + 两种仿真器的测量输出解析器 + 声明“读哪些测量名”，
  在 worker 内即时读取。成本约 2–4 天（含 fixture 与失败语义）。
- **B. 注入**：由库在网表中插入测量语句，需要网表模板/占位符与语法版本适配，
  成本 1–2 周以上，且触碰项目暂缓的 netlist DSL 边界。

优点：I/O 与内存大幅下降；覆盖问题天然消失（只需读取极小的测量文件）；指标由
仿真器在求解过程中直接计算，避免二次遍历大数据。

风险：表达能力有限（复杂派生、跨信号组合、优化目标仍需 raw）；测量缺失/写错
可能静默失败，必须建模为显式状态；输出格式随版本漂移，需要 fixture 契约；
不落 raw 会降低事后重算与可视化能力。

边界：库不定义业务指标、不做 optimizer；只解析“用户声明、仿真器计算”的量。

## 5. 备选：产物快照（兜底/过渡）

**机制**：job 完成后把产物复制到 `worker_<id>/case_<index>/`，`TaskResult.work_dir`
指向快照；语义与现有 `read_*` 完全兼容。

成本约 0.5 天；保留调试与事后重算能力；代价是多一次拷贝与磁盘占用。适合作为
“先修正确性”的过渡方案，也可与方案一组合（失败必留 raw）。

## 6. 方案对比

| 维度 | 快照 | worker 内即时提取 | 原生测量直出 |
|---|---|---|---|
| 实现成本 | 低（~0.5 天） | 中（1–2 天 MVP） | 中（直通 2–4 天；注入 1–2 周） |
| 根治覆盖 | 是 | 是 | 是 |
| 保留调试产物 | 是 | 取决于保留策略 | 默认丢失（需策略回退） |
| 大波形适配 | 差（拷贝大） | 中（不落盘则好） | 最好（不产生波形） |
| 吞吐影响 | 拷贝占用不大 | 解析占用 worker 时间 | 仿真器内部计算，落盘最少 |
| 指标表达力 | 不限（后处理） | 不限（库内计算） | 受仿真器测量语法限制 |
| 边界风险 | 无 | 需引入提取声明 | 需测量解析与版本契约 |

## 7. 推荐实施路线

1. **P0 修正确性**：先加“`workers=1` + 多 case，指标必须各不相同”的回归测试
   （当前必然失败）；选定快照或“标量级即时提取”之一立刻落地，默认策略
   “失败必留 raw”。
2. **P1 即时提取 MVP**：声明式标量/派生指标 + `TaskResult` 扩展 + Python 暴露；
   波形暂不内联。
3. **P2 原生测量直通**：`kMeasure` 与 Ngspice/Spectre 测量解析 + fixture 契约；
   采用混合策略——测量直出优先，未覆盖的指标回退 raw（按保留策略）。
4. **P3（可选，暂缓）**：网表模板/占位符注入测量语句，需先评估 netlist DSL 边界。

完成定义（P0/P1）：多 case 并发下每个结果读到的指标与输入参数一一对应；失败
任务保留可排查产物；默认构建与外部预设回归全绿。
