## 1. 背景与目标

SPICEUnion 的默认构建不依赖任何 EDA 工具；真实仿真（Spectre / Ngspice）测试需要
调用他人机器上“存在但不保证相同”的仿真器。当前已有几个分散的适配点：

- 通过 `SPICEUNION_NGSPICE` 环境变量显式指定 ngspice 可执行文件；
- 外部测试用 `GTEST_SKIP()` 表达“环境不具备”，并带文本原因；
- 结果读取由执行层声明 `ResultFormat`，解析层声明优先、未知才嗅探；
- 跨 backend 语义用“物理语义契约”（-3 dB、τ、分压比）而非逐版本黄金值钉住。

本专项把这些分散点收敛成一个**“自动体检 + 能力声明 + 显式失败”**的设计，回答一个
问题：换一台机器、换一个仿真器版本时，SPICEUnion 如何自动知道“有什么、能做什么、
缺什么”，并让用户得到可读的诊断。

**边界（先讲清“不做什么”）**：自动适配不等于万能兼容。SPICEUnion 只承诺在
“已声明能力”的范围内行为正确；对探测不到的仿真器、不支持的结果格式或缺失的私有
材料，一律给出结构化原因，而不是猜或硬凑。

## 2. 问题分层

把“适配”拆成四层，每层都对应可测试的产物：

| 层 | 职责 | 现状映射 |
|---|---|---|
| 探测 | 找到可执行文件、确认来源与版本 | `SPICEUNION_NGSPICE`、PATH 查找 |
| 能力 | 声明“支持哪些分析/格式/网表任务” | 半隐式（版本靠文档、门控靠 skip） |
| 门控 | 不可用时优雅降级并给出原因 | `GTEST_SKIP()` + `SPICEUNION_ENABLE_EXTERNAL_TESTS` |
| 验证 | 契约测试跨版本成立、校准测试只绑定确认环境 | RC 语义契约测试、真实网表校准断言 |

## 3. 设计要点

### 3.1 探测（Discovery）

解析器按固定顺序查找仿真器：

1. 环境变量显式指定：`SPICEUNION_SPECTRE` / `SPICEUNION_NGSPICE`；
2. `PATH` 查找（`spectre`、`ngspice` / `ngspice_con`）；
3. 常见安装点（conda envs、`/usr/local`、`/opt`），仅作为“诊断建议”，不作为默认
   装配，避免隐式劫持用户 PATH；
4. 运行 `--version` / `-version` 之类的稳定输出，解析版本与来源。

产物：统一结构 `SimulatorHandle{kind, executable, version, source}`。解析结果可缓存，
并提供“重新探测”入口（安装/升级仿真器后不需要重启进程）。

### 3.2 能力（Capabilities）

能力表按“仿真器类型 × 版本区间”声明，例如：

```text
ngspice >= 30 : rc_ac / rc_tran / resistor_divider_dc / nspice_wrdata
spectre >= 15 : interactive / psfascii / binpsf(dc,ac,tran)
```

版本只作**快筛**，真实行为以**动态最小探针**为准：需要时跑一次最小网表（毫秒级），
确认输出格式、文件名约定等关键事实。能力对象公开给上层：

```text
SimulatorCapabilities
  -> supported_analyses
  -> supported_result_formats
  -> builtin_ngspice_tasks
```

核心约束：**核心执行/解析逻辑不得按版本号 if-else**；差异一律收敛到能力表或适配器
注册表，新增仿真器版本 = 新增能力条目 + 契约测试，而不是改核心代码。

### 3.3 门控与错误分类（Gating / Diagnostics）

门控输出机器可读的分类，替代现在只有自由文本的 skip 原因：

```text
not_found            仿真器不存在（含建议安装方式）
unsupported_version  存在但低于能力表下限
material_missing     依赖私有网表 / PDK，材料未配置
format_unsupported   仿真可跑但结果格式当前不支持
```

诊断入口建议形态：`spiceunion doctor`（或等价 demo）一次性输出：

```text
[ngspice] found: ngspice 41 (conda env ngspice_new)
          builtin tasks: rc_ac / rc_tran / resistor_divider_dc ... ok
[spectre] not_found: 未在 PATH / SPICEUNION_SPECTRE 找到
          suggestion: ...
```

## 4. 模块与 API 切分建议（实施时按此细化）

- 公开头文件 `include/su/toolchain.hpp`：`SimulatorHandle`、
  `SimulatorCapabilities`、`SimulatorDiagnostic` 与探测入口；
- 实现目录 `src/toolchain/`（或并入 `src/session/`，按“是否会被普通用户 workflow
  使用”决定）：resolver、版本解析、能力表、最小探针；
- `SimulationOptions` / `Simulation` 只透传“优先用哪个仿真器”，不吞掉探测失败；
- 诊断命令可先落在 `tests/manual/` 或示例程序，成熟后再进入正式入口；
- Python binding 是否暴露 `spiceunion.doctor()` 作为后续项，不在第一版承诺。

## 5. 测试策略

探测与能力逻辑用**可控假环境**做单元测试：测试通过临时 PATH / 环境变量注入假
可执行文件（写版本号、返回码），不依赖真实仿真器。

测试分两类，规则写进约定：

| 类型 | 覆盖 | 进通用 CI |
|---|---|---|
| 契约测试 | 语义在受支持版本区间内成立 | 是（云 CI 零 EDA 或自托管矩阵） |
| 校准测试 | 绑定具体版本 + 私有材料的黄金值 | 否（只在确认环境手动/自托管跑） |

## 6. 完成定义（供路线图引用）

- 探测层可输出 `SimulatorHandle`，覆盖 Spectre / Ngspice 的 env 与 PATH 路径；
- 能力层能回答“该环境支持哪些 builtin 任务与结果格式”；
- 门控层所有外部测试的 skip 都有机器可读分类 + 人类可读建议；
- `spiceunion doctor` 在新机器上一次命令给出完整诊断；
- 上述均有默认测试覆盖，且不影响零 EDA 的默认构建。

## 7. 暂缓与边界

- 私有网表 / PDK 材料的“自动获取”不在本专项范围（只负责检测缺失并给出配置提示）；
- PSFXL 等结果格式边界仍以 `01_当前事实状态.md` 为准，本专项只负责让“不支持”
  这件事变得可发现、可解释；
- 不引入仿真器版本黄金值的通用 CI 矩阵（成本高、收益低），契约测试是主防线。

## 8. 承接关系

- M3 已建立跨 backend 语义契约，本专项把“能跑哪些 backend”形式化为能力表；
- M5/M6 的 `Simulation` facade 是诊断入口的消费方；
- CI 分层（云零 EDA / 自托管真实仿真）为本专项的验证矩阵提供执行场地。
